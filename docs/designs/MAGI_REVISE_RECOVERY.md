# Magi: REVISE後の原因分析と修正の契約

日付: 2026-09-11。状態: ローカル実装対象。配布・既存campaignの再開承認ではない。
確認基点: claude-harness `e9a7cf6da18834f6febd80d1d675e43bb944fa15`。

## 問題と原因

REVISEを受けた実装側が、原因を確かめる前に指摘箇所だけ変更し、同じ原因を残したまま
再レビューへ進んでいた。ユーザーは「症状→原因追求→根本修正」をMagiの契約にすることに合意した。

仮説は、既存の継続手順が原因分析を要求せず、修正・再レビューへ直結していることである。
確認対象を継続hookと各familyの修正手順に限定して照合した。

- `magi_autorun.py`のStop hookは予算・遷移・停滞・plateauを確認し、一般的な
  `apply in-scope fixes, run the next legal phase`を指示する。
- dual-magiの修正手順、bug-huntのFix now、ultramagiの修正ループには、
  調査前の仮説や修正前の原因説明を一貫して要求する段階がない。
- 既存の`root_cause_id`と再発判定は再利用できるが、claimの`success`自体は
  検証済みのREVISEを意味しない。hookがREVISEを自動判定しているとは扱わない。
- 停滞検出は対象文書とcampaign履歴を使うため、原因分析の記録だけが進んでも認識されない。

既存テストは停止・継続・予算等の制御を検証していたが、継続指示の因果分析手順と
原因分析記録による進捗を検証していなかった。今回の回帰試験はこの二つを対象にする。

## 不変条件と変更範囲

指摘を修正する際は、調査目的を定め、根拠から原因を説明し、修正の効果を検証してから
次の許可されたレビューへ進む。原因の作文、単なるファイル変更、reviewerの修正案の転記は
この契約を満たさない。

変更範囲は各familyのMagi技能手順と、既存Codex Stop hookの継続指示・停滞検出である。
一回限りのMagi preflightのPIVOT/ABORTにも、指摘へ対応する際の同じ契約を参照させる。
preflightを複数round化せず、追加の原因分析モデルやレビュー段階は作らない。

ローカルworktreeで文書・hook・合成テストを変更する可逆な作業とする。原本と配布済みplugin、
既存のレビュー記録・claim・予算は変更しない。作業を取り消す場合は、この差分を採用しない。

## 指摘を修正する側の契約

| 段階 | 必須の記録 | 次に進める条件 |
|---|---|---|
| reviewerの指摘 | 症状、期待する動作、発生条件と根拠 | 修正案を原因の証明として扱わない |
| 調査前 | 原因の仮説、支持/反証する観測、調査範囲 | 原因を断定せず、目的に沿った調査を行う |
| 修正前 | 観測から原因へ至る説明、関連caller/共通処理への影響、既存テストが見逃した理由、修正方針 | 仮説に反する結果は仮説へ反映する。未確定のまま製品修正しない |
| 再レビュー前 | 同じfixture・判定条件の修正前後結果、コードとテストの版、関連経路の検証 | 修正前は対象の症状で失敗し、修正後は期待を満たす。単なるimport失敗等を再現成功としない |

記録は既存のfinding/source参照と`root_cause_id`に結びつけ、根拠への参照を中心に短く保つ。
同じ原因が再指摘された場合は、前回の原因説明の誤り・不足と、前回の試験で検出できなかった
条件を先に訂正する。名前だけ変えた新しいrootとして履歴を切らない。

直接再現できなければ、理由と限界を示した静的な因果確認等を使い、反例と照合する。
根拠が不足する場合は未解決として残す。調査の範囲・時間を区切り、無関係な作業は継続できる。
文書や仕様の指摘では、修正前後の同じ整合性確認を証拠にできる。

形式不備・通信エラーは製品のREVISEと分ける。未検証の出力から製品修正を始めず、
既存の技術的な回復手順を使う。修正対象でない軽微な残課題や、根拠付きの不採用には
不要なコード変更や試験を要求しない。既存の残課題・スコープ・出荷権限の規則は維持する。

## hookへの接続と強制範囲

既存Stop hookは、REVISE等の修正対象がある場合に上記順序へ戻るよう条件付きで指示する。
対象別の短い記録を`.dual-magi/REPAIR.<document_id>.md`へ保存し、そのdigestを既存の
進捗fingerprintへ含める。本文はhook出力へ載せない。欠落は未作成として扱い、
不正な種別・symlink・上限超過の記録は可視の失敗として扱う。

技能手順とhookによる行動契約であり、任意のshell/編集操作を遮断するPreToolUse制御ではない。
記録のdigestは進捗検出用で、原因の正しさや修正完了の証明ではない。claim/admissionは
修正記録の内容を検証しない。OSによる編集禁止や、独立したテスト証明基盤の完成とは報告しない。
継続hookがないfamilyにも技能手順を適用するが、Codex用hookが稼働すると説明しない。

成功確定前のreviewer identity/参照結合検証は別の不具合であり、この変更で修復済みとはしない。
過去の不正な審査記録を後から修正したり、上限をリセットしたりして再開させない。

## 受入条件

1. 旧hookへの同じ試験は、原因分析手順の欠落・原因記録の進捗未認識で失敗する。
2. 修正後は調査前・修正前・再レビュー前と再発時訂正が継続指示に現れる。
3. 原因記録の更新は進捗になる。同じ記録での停止を繰り返せば従来の停滞上限が働く。
4. 記録の不正な種類や過大入力を拒否し、本文をhook出力へ漏らさない。
5. 未arm・終端・予算超過・有効/無効plateau等の既存挙動を維持する。
6. family間の原因分析契約と参照が一致し、一回限りのpreflight契約も維持する。

正式なレビュー・配布の受入は別に行う。本書とローカル試験を、既存campaignのplateauの代用にしない。
